Augmented Social Scientist: train encoder models on a classification task

Authors

A. Morin

Alban Derepas

Introduction

Social scientists working with large corpora of documents (tweets, abstracts, newspaper articles, videos…) often need to annotate each item with one or more labels to conduct analysis, such as the evolution of topics or modelisation. Common strategies include hiring interns, outsourcing to a company such as MTurk, or automating the task with various strategies. Since the development of LLMs, it has become common practice to use them as annotators in social science contexts (Gilardi et al., 2023; Bonikowski et al, 2022). For instance, such study annotated 4.5 million tweets addressed to French members of parliament with the labels “attack”, “critique” or “support” to describe the conditions of hate speech towards them on Twitter. In Machine Learning jargon, this is a “classification task”.

This tutorial is part of a series on using LLMs as annotators. A companion tutorial covers the generative AI (genAI) approach: writing a prompt and parsing the label out of the model’s response. Here, we cover another approach using specific models called encoders (an LLM that does not generate text1), fine-tuned on an annotated sample the way a human expert would learn the task2. This gives you more control over the model and its performance, at the cost of (a bit) more NLP knowledge and coding skill.

Why not just use ChatGPT? Generative models (GPT, Llama, Claude) are prompted: you describe your categories and hope the model interprets them as you would, every time. An encoder (BERT and its relatives) produces no text but an embedding, a numerical representation of a text’s meaning3, and is fine-tuned on texts you label yourself. You thus control the whole pipeline: the model can only assign the categories you defined, learned from your annotations and nothing else. A generative model brings everything it learned elsewhere into each decision, and may read into a text things that are not in it. Its errors are then not random but biased: Ashwin et al. (2025) found that a generative LLM’s coding errors on interviews with Rohingya refugees were correlated with respondents’ characteristics, whereas a model fine-tuned on human-coded transcripts showed less bias.

Using small models helps to keep your data confidential: encoders are light enough to run on your own machine or a trusted server4, so sensitive corpora never go through an external API. And they keep your results reproducible: closed generative models can change after an update, while you own the encoder and its fine-tuning data. Finally, they are cheaper to run on large corpora, and a few hundred annotated texts are often enough (Laurer et al., 2024; Bucher & Martini, 2024). The price is the annotation effort, more code, and a model that performs a single task. But even this cost has its avantage : you learn a lot during the annotation process.

This tutorial fine-tunes an encoder model: we load and format a dataset, load the model and set its hyperparameters, launch fine-tuning, assess performance, and tune hyperparameters to improve it. We close with advice on incorporating the results into a social science project, including hardware tips along the way.

NoteRefresher: the classification task in machine learning

The classification task is a concept from machine learning: an algorithm uses input data (the predictors) to assign a class, or label, to each input. Scikit-learn5 puts it this way: Identifying which category an object belongs to. The connection with annotation is direct: each text needs to be assigned a label, so annotating is a classification task.

Classification belongs to the supervised learning family: to assign labels, the algorithm must first be fitted on training data, in our case handmade annotations. Fitting (or training) consists of providing inputs and their labels, so that the algorithm adapts to the task and “learns” it. Social scientists therefore first need to annotate a small set of texts to train the classifier.

Classifiers often have structuring settings called hyperparameters, which shape how the algorithm learns and are not changed during training. They must be set with care to reach satisfying performance.

To evaluate classifiers, we use normalised metrics such as precision, recall, accuracy and the F1 score. Depending on your research, you may want to optimise one metric or another:

  • Precision: “out of all the elements predicted as class A, how many were indeed from class A?” This metric is rather conservative: optimising it limits the number of false positives.
  • Recall: “out of all the elements that should have been classified as A, how many were indeed classified as A?” This metric is more inclusive: optimising it limits the number of false negatives.
  • Accuracy: “across all classes, how many elements were classified correctly?” It can be misleading when classes are imbalanced: a model that always predicts the most frequent class can score high while never recognising the rare ones.
  • F1 score: the harmonic mean of precision and recall, which balances the two.

To assess a model correctly and prevent cherry-picking, we evaluate it on distinct subsets of texts and annotations:

  • The train set: the texts shown to the algorithm to learn from. Metrics on the train set are inflated, since the model has already seen these texts.
  • The valid set: texts used to assess the algorithm on new data, and to choose the hyperparameters. Metrics on the valid set are likely to be somewhat inflated too, since the hyperparameters were chosen to optimise them.
  • The test set: texts used once, at the end, to assess the algorithm with the chosen hyperparameters on new data. Metrics on the test set are meant to represent the algorithm’s performance on new data, and are the ones you should report, to avoid cherry-picking.

Key concepts and valuable resources to start your NLP journey

This tutorial fine-tunes a pretrained encoder model to perform a classification task. This section explains these terms, at a level sufficient to follow the rest of the tutorial.

The models used here are neural networks. Their behaviour is entirely determined by a large set of adjustable quantities called parameters (also known as weights and biases), and training a model means adjusting these parameters until it produces the output you expect.

An encoder turns a text into an embedding: a numerical representation of its meaning. Texts close in meaning get close embeddings, a proximity measured by a similarity score (Figure 1). BERT (Devlin et al., 2019) is the best-known encoder; CamemBERT (French), RoBERTa and ModernBERT are later variants. This tutorial uses bert-base-uncased.

Models don’t read words but tokens: words or pieces of words from the model’s vocabulary, into which texts are split before use. Every encoder has a context window, the maximum number of tokens it processes at once. Anything beyond is ignored, so long texts may have to be split into sentences or paragraphs (older models read 128 to 512 tokens). It is important for encoders since their context windows are smaller than generative models.

A pretrained model has already learned how a language works, by reading very large amounts of general text such as Wikipedia, books or web pages. This step requires computing power and data out of reach of most research teams, so it is done by companies and research labs, who often share the resulting models publicly; this tutorial downloads its model from Hugging Face, the main platform for doing so. Fine-tuning adjusts its parameters slightly with your annotations, to turn it into a classifier for your own labels. It is quick: a few minutes, at most a few dozen on limited hardware.

An encoder only produces embeddings, so going from an embedding to a category takes one more step: we add a classification layer on top of the encoder. This single linear layer takes a text’s embedding as input and produces one score per label, and the label with the highest score is the prediction. It starts with random parameters and learns your categories during fine-tuning, while the encoder’s own parameters are adjusted slightly.

Fine-tuning proceeds by small successive corrections: the model reads a batch of annotated texts, compares its predictions with your annotations, and adjusts its parameters slightly to reduce the gap between the two, called the loss. It then moves to the next batch, and repeats until it has gone through the whole train set: one epoch. The settings that control this loop (how many texts per batch, how large each correction is, how many epochs) are called hyperparameters; we introduce them when diagnosing training problems (Section 4.1).

To check that the model learned your categories rather than memorised your examples, annotations are split into three sets: the train set is used to optimise the weights by reducing the loss, the valid set is used during fine-tuning to measure the loss on texts that never update the weights, which shows whether the model is really learning and lets you compare settings, and the test set is kept aside for one final, unbiased score.

Fine-tuning pipeline: the essential

We use a dataset introduced by Luo et al. (2020): sentences extracted from journal articles, each annotated as “agreeing”, “neutral” or “disagreeing” with the statement “Climate change/global warming is a serious concern”. The pipeline:

  • Load, clean and split your data into train, valid and test sets.
  • Choose a model from Hugging Face and load it locally.
  • Fine-tune the model.
  • Assess performance and tune hyperparameters.
  • Predict labels for the full dataset.

Unwanted characters: unlike TF-IDF, transformer models are trained on punctuation and benefit from keeping it; strip only what carries no semantic value for your task (e.g. emojis, if your model doesn’t recognise them7). Here we just fix some punctuation irregularities:

def preprocess_text(text: str):
    if not(isinstance(text, str)):
        return pd.NA
    return (
        text
        .replace("``", '"')
        .replace("''", '"')
        .replace(" ,", ",")
        .replace(" .", ".")
        .replace(" !", "!")
        .replace(" ?", "?")
        .replace(" :", ":")
        .replace(" 's", "'s")
    )

df["sentence-preprocessed"] = df["sentence"].apply(preprocess_text)

Choose and load a model

We use the Transformers package, maintained by Hugging Face8, and start with google-bert/bert-base-uncased.

NoteHow to choose a model

Model performance is sensitive to task and context: try several and compare. Criteria to weigh:

  • Task: browse Hugging Face’s models by task; here, Text Classification.
  • Language: multilingual models can underperform monolingual ones on a single-language corpus; consider a monolingual model, or translating your corpus first.
  • Training/evaluation domain: performance varies by domain, so check the model’s documentation for benchmarks close to yours.
  • Relevance: download counts are a rough proxy for popularity and (to some extent) performance; a drop can signal a newer model has taken over.
  • Size: your hardware sets a hard ceiling: know it, and check what you can run given it.

We load it with an AutoModel class9, here AutoModelForSequenceClassification:

from transformers import AutoModelForSequenceClassification, set_seed

set_seed(SEED) # The classifier layer is initialised randomly: fix the seed here too

labels = list(df["label_text"].unique())
num_labels = len(labels)
id2label = {id:label for id, label in enumerate(labels)}
label2id = {label:id  for id, label in enumerate(labels)}

MODEL_NAME = "google-bert/bert-base-uncased"
model = AutoModelForSequenceClassification.from_pretrained(
    MODEL_NAME,
    num_labels=num_labels,
    id2label=id2label,
    label2id=label2id,
)

Fine-tune the model

Three steps remain: tokenize the dataset, set the training arguments, and launch training.

Tokenize the dataset

Tokenizing happens in two steps: text is split into tokens from the model’s vocabulary, then each sequence is truncated or padded to a fixed length.

Load the tokenizer10 the same way as the model:

from transformers import AutoTokenizer

tokenizer = AutoTokenizer.from_pretrained(MODEL_NAME)
TipExample 
tokenizer("Hello World! 😇")
# {'input_ids': [101, 7592, ...], 'token_type_ids': [0, 0, ...], 'attention_mask': [1, 1, ...]}
tokenizer("Hello World! 😇").input_ids
# [101, 7592, 2088, 999, 100, 102] <- the token ids
tokenizer.decode([101, 7592, 2088, 999, 100, 102])
# '[CLS] hello world! [UNK] [SEP]'
# [CLS] is the starting token and [SEP] the terminating one.
# The smiley is marked as unknown [UNK]
tokenizer.decode([101])
# '[CLS]' <- token number 101
tokenizer.decode([2088, 999])
# 'world!' <- tokens number 2088 and 999
tokenizer(
  ["This sentence is very long. " * 20, # Very long
   "Short."],                           # Very short
  truncation = True,
  padding = "max_length",
  max_length = 50,
  return_tensors = "np"
).input_ids.shape
# (2, 50) <- long entries are truncated and short ones are padded so that all tokenized entries are the same length

Set the tokenizer’s parameters inside a preprocessing function and apply it:

def preprocess_dataset(row: dict):
  tokenized_entry = tokenizer(
    row["sentence-preprocessed"],
    truncation = True,
    padding = "max_length",
    max_length = 400,
  )
  return {
      **row.copy(),
      "labels": int(label2id[row["label_text"]]),
      **tokenized_entry
  }

dsd = dsd.map(preprocess_dataset)
# Only keep columns useful for training
dsd = dsd.select_columns(['ID', 'labels', 'input_ids', 'token_type_ids', 'attention_mask'])

Setup fine-tuning hyperparameters

Fine-tuning parameters live in the TrainingArguments11 object. Below are the main ones; the full list of 117 parameters is in the documentation. What each hyperparameter does, and how to tune it, is covered in Section 4.1.

from transformers import TrainingArguments, Trainer
training_arguments = TrainingArguments(
    # Hyperparameters
    num_train_epochs = 5,
    learning_rate = 5e-5,
    weight_decay  = 0.0,
    optim = "adamw_torch_fused",
    # Second order hyperparameters
    per_device_train_batch_size = 4,
    per_device_eval_batch_size = 4,
    gradient_accumulation_steps = 8,
    # Pipe
    output_dir = "./models/training",
    eval_strategy = "steps"   , eval_steps    = 0.05,
    logging_strategy = "steps", logging_steps = 0.05,
    save_strategy = "steps"   , save_steps    = 0.05,
    load_best_model_at_end = True,
    save_total_limit = 2,
    seed = SEED,

    disable_tqdm = False,
)

This produces a list of folders12, each holding:

  • config.json: the model config, similar to AutoConfig.
  • model.safetensors: all model weights.
  • optimizer.pt, rng_state.pth, scheduler.pt: the optimizer, RNG state and scheduler at that point.
  • trainer_state.json: metadata up to that checkpoint.
  • training_args.bin: a copy of the training arguments.

trainer.state.best_model_checkpoint holds the path to the best one, where validation loss reaches its minimum: here, checkpoint 60 ('./models/training/checkpoint-60'), with a validation loss of 0.80. Reload a checkpoint the same way as the original model:

reload_model = AutoModelForSequenceClassification.from_pretrained(
    trainer.state.best_model_checkpoint)

Use model for inference and evaluate performance

Once you have a new fine-tuned model, you can use it on elements to predict the label. But we also need to verify that those predictions are correct.

To do so, we predict labels on the valid set (Section 3.1), then compare against the gold annotations using standard metrics: accuracy, precision, recall, F1. We use a dedicated valid set to be able to compare different versions of a model, and different models, on the same standard.

import numpy as np
import torch
from tqdm import tqdm

IDs = []
y_gold = []
y_pred = []

# Reload the best model:
model = AutoModelForSequenceClassification.from_pretrained(trainer.state.best_model_checkpoint)
model.eval()

for batch in tqdm(dsd["valid"].iter(batch_size = 8)):
  IDs += [batch["ID"]]
  y_gold += [batch["labels"]]
  with torch.no_grad():
    logits = model(input_ids = batch["input_ids"], attention_mask = batch["attention_mask"]).logits.softmax(1).numpy()
    y_pred += [np.argmax(logits, axis=1)]
results = pd.DataFrame({
  "ID": np.concat(IDs),
  "gold": np.concat(y_gold),

What’s a good score?

There’s no universal “good enough” threshold: it depends on the task. Compare against these instead of judging the raw number alone:

  • A trivial baseline: how would always predicting the majority class, or guessing at random, score? Barely beating that means the model hasn’t learned much.
  • Human agreement: inter-annotator agreement from your own annotation process (e.g. two coders on a shared sample) is a realistic ceiling: texts humans disagree on, the model won’t reliably get right either. Approaching that agreement is about as good as it practically gets.
  • Intended use: an exploratory, descriptive use (e.g. roughly characterising prevalence over time) tolerates more noise than a causal claim, where misclassified items can bias conclusions in a specific direction.

As a rough rule of thumb, macro F1 in the 0.7–0.9 range is typical for a usable social science classifier, but validate against the criteria above, not the number alone.

Once you’ve settled on a model and its hyperparameters, run the same code once on dsd["test"]: since none of your choices were based on it, this is the unbiased score to report.

Training pipeline: advanced practices

Diagnose and fix training problems

Checkpoints from Section 3 include the learning curve, which tracks the loss as fine-tuning progresses. The loss measures the gap between the model’s predictions and your annotations: the lower, the better. As a reference point, a model guessing at random between our 3 labels gets a loss of about 1.1, close to where our curves start.

The curve shows the loss on two sets of texts (Section 3.1), which play different roles during fine-tuning:

  • The train set is used to optimise the weights: each correction aims to reduce the loss on these texts, so the train loss is expected to keep falling.
  • The valid set is also used during fine-tuning, but for inference only: at regular intervals (here every 12 steps) the model predicts the labels of these texts, and its weights are never updated from them. The valid loss therefore shows whether the model is actually learning, rather than memorising the train set, and when to stop training. Once the valid loss stops falling, more training no longer helps.

Retrieve both from the trainer14 and plot them:

import plotly.express as px

loss = []

for log in trainer.state.log_history:
    step = log["step"]
    if "loss" in log:
        loss += [{"step": step, "loss": log["loss"], "split": "train"}]
    elif "eval_loss" in log:
        loss += [{"step": step, "loss": log["eval_loss"], "split": "valid"}]
    else:
        print(log)

loss = pd.DataFrame(loss)

px.line(loss, x = "step", y = "loss", color =  "split")

Train loss decreases steadily towards 0, while valid loss decreases, reaches a minimum, then rises: the model is memorising the train set past the point where it stopped generalising better, which is why we reload the checkpoint at the minimum (Section 3.4), not the last one. What matters is how low that minimum is, and how the two curves sit relative to each other. The pattern to aim for:

The perfect case

  • Both curves went down: the model learned.
  • Both curves sit at similar values: no overfitting.
  • Both are flat at the end: nothing more to learn.

Once your curve looks like this, check the evaluation metrics for prediction quality. If it doesn’t, one of the problems below is the likely cause, and each comes with the hyperparameters that fix it.

Problem 1: the model hasn’t learned enough

At one extreme, both curves stay flat (left): metrics are barely better than chance, and the corrections were too small or too few. At the other, both curves are still falling with no plateau (right): the model is learning correctly, just not finished.

  • Learning rate 🟢🟢🟢 (importance) sets the size of each correction. It is the most consequential hyperparameter. Too low, fine-tuning leaves the model essentially unchanged; try increasing it. Typical values: \([1e-6, 1e-4]\).
  • Number of epochs 🟢 sets how many passes through the training set. If performance was still improving when training stopped, add more. Typical values: 3-5 (more costs more compute time).

Problem 2: the model has learned your training set by heart

The model performs well on texts it trained on and noticeably worse on valid: both curves fell, but train sits much lower than valid. It has memorised the training examples instead of learning the underlying distinction. This is overfitting, the most common failure here, especially with few annotations.

  • Weight decay15 🟢🟢 discourages extreme parameter values, the usual mechanism behind memorisation. Increasing it constrains the model toward more general solutions; too high and it can’t learn at all. Typical values: 0.01-0.1.
  • Lowering the learning rate or epochs works the same way: fewer, gentler corrections leave less room to fit the specifics of your examples.
  • The most reliable fix isn’t a hyperparameter: annotate more data.

Problem 3: the fine-tuning is erratic

Performance swings between evaluations instead of improving steadily: corrections are computed on too little evidence at a time, each chasing the quirks of a handful of texts rather than a general pattern.

  • Batch size 🟢🟢 is how many texts the model reads before each correction. Larger batches reflect the corpus’s general tendency rather than individual noise. Typical values: 16-64.
  • A learning rate set too high causes the same symptom for a different reason: each correction overshoots. Lower it if enlarging the batch isn’t enough.

Problem 4: the fine-tuning does not fit on your machine

This doesn’t show up on the learning curve: a large batch must be held in memory at once, which is usually where a personal computer gives up (Section 4.2). Accumulate several small batches before applying a correction instead. It is nearly equivalent, and uses far less memory:

\[\text{Batch size} = \text{Device batch size} \times \text{Gradient accumulation steps}\]

  • Device batch size is what your hardware actually processes at once: lower it until training fits in memory.
  • Gradient accumulation steps compensates, keeping the effective batch size where you wanted it.

Disk space needs the same care. Eval and save strategies 🔴 can be "epoch" or "steps"; with "steps", eval_steps and save_steps set how often the model is evaluated and saved. Checkpoints can weigh several gigabytes, so cap how many are kept with save_total_limit16.

TipWhere to start

Change the learning rate first. Keep everything else at the values from Section 3.3.2, try a few learning rates spanning the typical range (e.g. 1e-5, 3e-5, 5e-5), and compare the resulting curves. Only then tune weight decay and batch size, and always compare on the valid set, never the test set.

Use GPU for faster training

Only relevant if you have a GPU. Otherwise, training on CPU works exactly as shown, just slower; skip ahead to Section 4.3. An NVIDIA GPU17 with cuda set up, or a Mac with an Apple M-series chip, accelerates training via cuda or mps respectively.

Check whether cuda/mps are available18:

from torch.cuda import is_available as cuda_available
from torch.mps import is_available as mps_available

print("CUDA: ", cuda_available())
print("MPS: ", mps_available())

Trainer detects an available GPU and uses it automatically: the fine-tuning code above runs on it unchanged. On an NVIDIA GPU, you can also enable faster, lower-precision computations:

# Choose your device
DEVICE = "cuda" # or "mps", or "cpu"

training_arguments = TrainingArguments(
  ...
  bf16 = DEVICE == "cuda", # Only on recent NVIDIA GPUs
)

Your own inference loop, however, must put the model and its inputs on the same device:

IDs = []
y_gold = []
y_pred = []

# Reload the best model:
model = AutoModelForSequenceClassification.from_pretrained(trainer.state.best_model_checkpoint)
model = model.to(device=DEVICE)
model.eval()
if DEVICE == "cuda": model = model.to(torch.bfloat16) # Only works on GPUs

for batch in tqdm(dsd["valid"].iter(batch_size = 8)):
  IDs += [batch["ID"]]
  y_gold += [batch["labels"].cpu()]
  with torch.no_grad():
    probs = (
      model(input_ids = batch["input_ids"].to(DEVICE), attention_mask = batch["attention_mask"].to(DEVICE))
      .logits.cpu().softmax(1).float().numpy()
    )
    y_pred += [np.argmax(probs, axis=1)]

results = pd.DataFrame({
  "ID": np.concat(IDs),
  "gold": np.concat(y_gold),
  "pred": np.concat(y_pred)
})

Moving elements incorrectly produces this error:

Expected all tensors to be on the same device, but found at least
two devices, cuda:0 and cpu! (when checking argument for argument
index in method wrapper_CUDA__index_select)

Clean up the GPU after use, or memory clogs and flushing it becomes a hassle. Wrap training in a try/except/finally block:

from gc import collect as gc_collect
from torch.cuda import empty_cache, synchronize, ipc_collect
from torch.cuda import is_available as cuda_available

tokenizer, model, dsd, trainer = (None, ) * 4 # All objects that are moved to the GPU
try:
  tokenizer = ...
  dsd = ...
  model = ...
  trainer = ...
  trainer.train()

except Exception as e:
    print("# ERROR" + "#" * 93)
    print(e)
    print("#" * 100)

finally:
    del tokenizer, model, dsd, trainer # All objects that are moved to the GPU
    empty_cache()
    if cuda_available():
        synchronize()
        ipc_collect()
    gc_collect()

Read the errors

You will face many errors. Some are random: rerunning the script or restarting the kernel fixes them. Others are subtler: search the exact error message (genAI is often less reliable here than a forum post from someone who hit the same issue), and remember that a library version mismatch is a common root cause. The four below are the most common; treat this as a reference, not required reading.

NoteDataset formatting

Most formatting errors come from columns not matching what the code expects:

  • "text": the text, as a string.
  • "labels": the label(s), as an int (or int tensor, if multi-label).
  • "input_ids": tokens truncated/padded to equal length, as an int tensor.
  • "attention_mask": same shape as input_ids, as an int tensor.

Column names can differ by model, so check that model’s documentation.

NoteMemory overflow

On GPU:

NVML_SUCCESS == r INTERNAL ASSERT FAILED at "/home/conda/feedstock_root/build_artifacts/libtorch_1750199048837/work/c10/cuda/CUDACachingAllocator.cpp":1016, please report a bug to PyTorch.

You’ve hit your hardware’s memory limit. Reduce the device batch size or use a smaller model. On CPU, the same issue shows as Invalid buffer size:.

NoteTensor shapes 
ValueError: too many values to unpack (expected 2)

Usually a tokenization issue. dsd["train"][0]["input_ids"].shape should return torch.Size([400]), not torch.Size([1, 400]): make sure the tokenizer isn’t called with return_tensors="pt", and that you use dsd.with_format("torch").

NoteMissing keys when saving/reloading a checkpoint 
There were missing keys in the checkpoint model loaded: ['bert.embeddings.LayerNorm.weight', ...
There were unexpected keys in the checkpoint model loaded: ['bert.embeddings.LayerNorm.beta', ...

A naming-convention mismatch (some models/versions use beta/gamma instead of weight/bias), resolved automatically. If performance is unexpectedly low afterwards, that may be a sign it wasn’t, and you’d then need to rename the parameters yourself, though this is rare.
